可靠工業設備整合參考架構

以設備事件、離線狀態與可復原處理為核心的規劃，呈現單次請求成功無法揭露的失敗情境。

適用團隊

工業 IoT、機器人與設備平台工程團隊

成果與界線

預計驗收：能從模擬設備追蹤一個事件到處理結果，包含重試與去重。

證據與範圍

使用合成資料的示範規劃。尚未建立連線設備群，也不是已部署機器人軟體的證據。

案例章節

問題業務情境限制工程決策故障情境可靠性策略安全與權限取捨預期成果與驗收系統架構技術與實作狀態

問題

網路中斷、晚到事件、寫入狀態後 worker 重啟，都是局部失敗；畫面不能把它們誤判為端到端正常。

業務情境

參考設計展示遙測如何成為可追蹤營運事件。目標是設備周邊整合，不宣稱運動控制、安全認證或實體部署經驗。

限制

僅使用模擬設備，先建立一條 REST 與一個 worker，再考慮 MQTT。ONLINE、OFFLINE、WARNING、ERROR、MAINTENANCE 是設備狀態，和訊息處理狀態分開；heartbeat 時限與過期政策須明定。

系統架構

工程決策

只追加的事件歷程與最新設備狀態分開。穩定事件 ID 用於去重，排序依設備序號或事件時間政策。持久處理後才確認訊息；OFFLINE 只是定義時間窗內未觀察到活動，不代表設備實體故障。

故障情境

規劃模擬網路逾時、重複、亂序、斷線、延遲、重試與 worker 故障。相同 ID 卻不同 payload 是衝突；較舊事件可以保留歷史，但不直接覆蓋最新狀態。

可靠性策略

定義有限重試、終止狀態、安全重播與關聯 ID，以固定時鐘重現離線測試。持久寫入前後中斷都需驗證不重複產生業務效果，並分開記錄接收、佇列等待與設備活性。

安全與權限

公開參考使用合成身份，不提供設備控制命令。真實接入須裝置認證、傳輸保護、payload 限制、授權和憑證輪替；模擬不證明正式安全或工業安全。

取捨

佇列有助解耦但增加維運依賴；至少一次投遞需要應用冪等性。嚴格排序可能延遲新事件，接受晚到資料則需要對帳政策。

預期成果與驗收

未來應能啟動參考程式、注入失敗、檢視事件與重試，解釋最後狀態。目前尚未建立或測試模擬器；客戶 pilot 應先限定一種事件與一條流程。

技術與實作狀態

  • 規劃：.NET 接收 API
  • 先 REST，後續 MQTT
  • 佇列
  • SQL
  • TypeScript 儀表板

示範與畫面

目前沒有可操作的模擬器或已連接設備。故障注入、狀態 UI 與截圖留待獨立專案。

程式碼與 repository 狀態
