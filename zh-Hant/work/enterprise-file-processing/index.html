問題

請求成功不代表後續檔案處理完成。單一 timeout 無法告訴操作人員該等待、重送還是調查，因此需要可檢視的生命週期。

業務情境

原本約 30 MB 的檔案限制，面臨成長至多 GB 的需求。設計重點是把長時間工作移出請求路徑；這不代表任何最大檔案已完成 benchmark。

限制

ASP.NET／.NET、IIS、SQL Server、RabbitMQ 與 Azure Blob 的限制都須考慮，包括磁碟、網路、串流生命週期與 worker 資源。資料庫、檔案、佇列與物件儲存沒有共同的原子交易。

系統架構

工程決策

以佇列分離請求和 worker，SQL 記錄已接收與已完成的差別。Manual Ack 在應用處理後確認；Prefetch = 1 在設定的消費者／channel 範圍內限制未確認訊息，不保證全域排序或恰好一次處理。保留可復原的本地檔案並明確釋放串流。

故障情境

Blob 已寫入但尚未 Ack 就中斷時，重送必須對帳而非再次產生業務效果。WAITINGFILE 的精確轉移與逾時規則仍需確認。NACK 不等於完整重試策略，無限 requeue 會困住毒性訊息。資料庫成功但發佈失敗也須對帳；outbox 僅是未來參考實作候選。

消費者 Ack 與發佈者確認是不同界線。新實作還需檢查發佈確認、路由結果及未發佈工作的對帳，不能只靠消費者 Ack 推定訊息已可靠進入佇列。

可靠性策略

按至少一次投遞設計冪等處理。ETag 表示物件版本，可用於條件操作，不能當成通用內容雜湊；重建時須定義檔案大小與 hash 檢查。原始驗證演算法未獨立查核。DLQ 是延伸概念，仍須示範重試耗盡、終止紀錄、安全重播與清理復原。

安全與權限

新部署必須認證上傳請求並授權每個檔案的存取，保護憑證、驗證路徑與檔名、限制上傳與資源，並定義暫存檔保留及清理政策。這些是新部署的要求，不是已查核原始系統具備的控制。

取捨

低 prefetch 有助控制未確認訊息壓力，但不代表整個系統只有一個序列式 worker。暫存檔可協助仍可存取該檔案的主機復原，不能替代複寫儲存；主機損毀、跨 worker 檔案存取、磁碟預算與孤立檔清理都需設計。Hot／Cool 選擇應依存取頻率、保留期及取回成本評估。

預期成果與驗收

本案例展示非同步交接與復原思考，沒有稽核過的延遲、吞吐、可用性、成本或商業效益數字。小型 pilot 應驗證中斷、重複投遞、內容損毀、檔案不可用與重試耗盡。
