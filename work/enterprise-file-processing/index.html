Reliable Asynchronous File Processing for Enterprise Systems

Separate file acceptance from long-running processing, track each handoff and recover safely when work is interrupted.

Who this is for

Enterprise teams managing file workflows and backend integrations

Outcome / boundary

An explicit processing lifecycle and recovery-oriented architecture. Multi-GB requirements are context, not a verified throughput or capacity result.

Evidence & scope

An anonymized account of enterprise engineering experience. Architecture and decisions are based on the engineer’s supplied project account. Proprietary implementation, customer identifiers and operational records are not published. No independent performance result is claimed here.

The problem

A file transfer becomes an operational problem when the request succeeds but downstream processing is incomplete. A timeout alone cannot tell an operator whether to retry, wait or investigate.

Business context

The original file limit was around 30 MB, while requirements were moving toward multi-GB files. The engineering question was how to decouple long-running work from the request and keep its state inspectable. This describes requirement growth; it does not assert that any particular maximum size was benchmarked.

Constraints

The stack combined ASP.NET / .NET, IIS, SQL Server, RabbitMQ and Azure Blob Storage. Request limits, local disk capacity, network interruption, stream lifetime and worker resource use all mattered.

The database, local filesystem, queue and object store do not share one atomic transaction. A successful step therefore cannot be treated as proof that the whole workflow is complete.

Architecture

Key engineering decisions

Move downstream processing behind a queue so the upload request is separated from worker execution. Keep lifecycle state in SQL so operators can distinguish accepted work from completed storage.

Use manual acknowledgements so delivery completion follows application processing. Prefetch = 1 limits unacknowledged deliveries to control worker pressure; it is a workload choice, not a universal performance optimization. It does not guarantee global ordering or exactly-once processing.

Keep a recoverable local artifact until the durable handoff is validated. Dispose streams explicitly so file handles and resource lifetimes do not prevent cleanup or accumulate across jobs.

Failure scenarios

Worker stops after Blob upload but before acknowledgement: redelivery may occur. Idempotent processing must reconcile the existing object and lifecycle record rather than create a second business operation.

Message arrives while a file is unavailable: the supplied account includes a WAITINGFILE state. The precise transition rules and timeout policy must be verified before rebuilding the original implementation.

Transient storage failure: retain recoverable work and apply a bounded retry policy. A NACK is not itself a retry strategy; requeueing indefinitely can trap a poison message.

Database succeeds but queue publication fails: pending work needs reconciliation. An outbox is a candidate improvement for a clean-room reference, not a verified feature of the original system.

Reliability strategy

Treat delivery as at-least-once and design business effects to be idempotent. A restart should answer: what has already happened, what is safe to repeat, and who owns a terminal failure?

ETags identify an object version and support conditional operations; they are not a general content checksum. A reconstructed reference should define explicit size and content-hash validation. The original validation algorithm is not independently verified here.

Dead-letter handling is an extension concept in the supplied material. A future reference must demonstrate retry exhaustion, a terminal record, safe replay and cleanup recovery rather than merely name a DLQ.

Security & permissions

The public case omits employer names, proprietary source, credentials, internal paths and customer documents. It describes the architecture without publishing private implementation details.

For a new deployment, authenticate upload requests, authorize access to each file, scope storage credentials, validate paths and filenames, define upload limits, and set retention. These are deployment requirements, not claims about verified controls in the original system.

Trade-offs

Low prefetch reduces concurrent pressure but can limit throughput. Local staging makes recovery possible but needs disk budgets and an orphan-file policy. Asynchronous processing requires meaningful progress states and operational support.

Hot / Cool storage is an access-pattern decision involving retrieval, retention and cost. No cost saving is claimed without workload measurements and current pricing.

Results & claim boundary

This case demonstrates reasoning about asynchronous handoffs, lifecycle tracking and recovery. It does not provide audited latency, throughput, uptime, cost or business impact numbers.

A small pilot would validate interruption recovery, duplicate delivery, corrupt or incomplete content, unavailable local files and retry exhaustion against an agreed workload.
