Supplier Quality & Operations Assistant

The implemented slice looks up synthetic quality procedures and exposes the exact source excerpt, version and section. A query or role change clears old results; insufficient evidence and a simulated unavailable source have separate outcomes.

Optional next steps: trace supplier–part–batch relationships against structured records, calculate metrics using deterministic code, and prepare a work-order draft. Those capabilities are not implemented. Any future write needs trusted identity, explicit approval, argument validation, an operation record and reconciliation after uncertain results.

The problem

A late delivery is not just a red row. An operations team needs to know which part is affected, what inventory is available, who owns the follow-up and whether the next action is overdue.

Business context

Supplier updates, purchasing data and quality notes often arrive through different channels. This proposed operational layer reconciles one workflow around existing systems. It does not claim to replace ERP or MES.

Architecture

Constraints

Use only invented suppliers, purchase orders, parts, dates, owners and inventory. No enterprise connectivity is implied. The proposed dashboard will use deterministic rules and notification previews. The current SOP lookup has neither notifications nor order-processing rules.

Key engineering decisions

Start with a delayed purchase order → affected part → shortage assessment → accountable action. Keep the original imported record distinct from human follow-up so operators can distinguish source data from a decision.

Use explicit exception states and ownership. Acknowledging an issue must not silently mark a purchase order as delivered or change source-of-truth inventory.

Failure scenarios

Reject missing part IDs and invalid dates with row-level feedback. Flag stale updates and duplicate records. An unavailable source should show its last successful update and stop presenting old data as current.

An unassigned exception remains visible. The proposed dashboard would escalate an overdue action. Empty results should say whether there are no issues or whether input data is missing.

Reliability strategy

Use a fixed demo clock and seeded data so expected results can be reproduced. Test the rule boundary for a delayed order, insufficient inventory and a blocked quality disposition.

Acceptance includes loading, empty, validation and error states; dashboard totals must reconcile to visible records. Notification delivery and production integration are separate later work.

Security & permissions

Display the synthetic-data label at the demo entry and dashboard. A real pilot needs authenticated owners, read/write boundaries, audit policy and an approved data contract before accessing an enterprise system.

Trade-offs

Batch imports make a first workflow easier to inspect but are not live inventory. Simple rules are explainable but depend on agreed stock, date and exception definitions. Supplier performance widgets require transparent denominators and period boundaries.

Expected outcome & acceptance

The future dashboard should show open issues, delayed orders, quality issues, shortage risks, recent exceptions, supplier performance and overdue actions from one consistent synthetic dataset.

The broader operational milestone is complete only when an operator can follow a delayed order through risk, owner assignment and resolution history. No time-saving or supplier improvement is claimed before measurement.

Technology

  • Proposed: .NET / Python API
  • Proposed: SQL and CSV / Excel boundary
  • Implemented: TypeScript fixture lookup
