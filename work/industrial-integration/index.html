Reliable Industrial Device Integration Reference Architecture

A planned reference for device events, offline states and recoverable processing—built around the failures a successful request does not reveal.

Who this is for

Industrial IoT, robotics and device-platform engineering teams

Outcome / boundary

Planned acceptance: one event can be traced from simulated device to processing outcome, including retries and duplicate suppression.

Evidence & scope

Demo environment using synthetic data. This is a planned reference architecture, not a connected device fleet or evidence of deployed robotics software.

The problem

Device fleets fail in partial ways: a network link disappears, a delayed message arrives after a newer event, or a worker restarts after changing state. A dashboard must not mistake these conditions for a healthy end-to-end system.

Business context

The reference will show how telemetry becomes an operational event that an engineer can inspect. It targets integration capacity around devices and robotics platforms; it makes no claim about motion control, safety certification or physical deployment experience.

Constraints

Use simulated devices only. Start with one REST ingestion path and one worker before adding an MQTT adapter. Device health and message-processing status are separate concepts.

Planned device states are ONLINE, OFFLINE, WARNING, ERROR and MAINTENANCE. The accepted heartbeat window and stale-event policy must be part of the demo contract.

Architecture

Key engineering decisions

Keep an append-only event history separate from the latest device state. A stable event identity enables duplicate detection; ordering uses a documented device sequence or event-time policy, not arrival time alone.

Acknowledge queue work after durable processing. A replay after worker failure must not duplicate the business effect. Treat OFFLINE as a liveness observation with a defined timeout, not proof of a physical device failure.

Failure scenarios

The simulator must trigger network timeout, duplicate event, out-of-order message, device disconnection, delayed message, retry and worker failure. Each scenario needs a visible event history and an expected state transition.

A duplicate with a changed payload is a conflict, not an ordinary replay. An older valid event may remain in history without overwriting the current device projection.

Reliability strategy

Specify a bounded retry schedule, terminal failure state, safe replay and processing correlation. Use a deterministic clock for stale/offline tests so timing failures can be reproduced.

Tests should interrupt processing before and after the durable write and confirm no second business effect on redelivery. Metrics and logs must distinguish intake, queue age, worker outcome and device liveness.

Security & permissions

The public reference will use synthetic identities and no device-control commands. A real pilot requires device authentication, transport protection, payload limits, authorization and safe credential rotation. Simulation does not validate production security or industrial safety.

Trade-offs

Queues improve decoupling but add operational dependencies. At-least-once delivery requires application-level idempotency. Strict ordering may delay fresh updates; accepting late events requires a clear reconciliation policy.

Expected outcome & acceptance

A future engineer should be able to launch the reference, inject a failure, inspect the event and retry history, and explain the final device state. This milestone provides that scope; it has not built or tested the simulator.

A small client pilot would integrate one event source and one operational workflow before considering a wider fleet deployment.

Technology

  • Proposed: .NET ingestion API
  • REST first / MQTT later
  • Queue
  • SQL
  • TypeScript dashboard

Screenshots & demo

No live simulator or connected devices yet. Failure injection, lifecycle UI and screenshots follow in the independent demo project.
