企業向けの信頼性を考慮した非同期ファイル処理

ファイル受付と長時間の処理を分離し、引き渡しを追跡して中断から復旧する設計。

対象チーム

ファイル処理・バックエンド連携を行う企業チーム

成果と適用範囲

明示的な処理ライフサイクルと復旧設計。数 GB は要件の背景であり、検証済み容量やスループットではありません。

この事例の内容

課題業務上の背景制約設計判断障害シナリオ信頼性の設計セキュリティと権限トレードオフ期待する成果と受入確認アーキテクチャ技術と実装状況

課題

リクエスト成功は後続処理の完了を意味しません。タイムアウトだけでは、待機、再送、調査のどれが必要か判断できないため、確認可能な状態が必要です。

業務上の背景

約 30 MB の制限から数 GB を扱う要件へ拡大する中で、長時間の処理をリクエスト経路から分離することが課題でした。特定の最大サイズを検証したという主張ではありません。

制約

ASP.NET／.NET、IIS、SQL Server、RabbitMQ、Azure Blob の制約に加え、ディスク容量、ネットワーク、ストリームの寿命、worker 資源を考慮します。DB、ファイル、キュー、ストレージは共通の原子的トランザクションを持ちません。

アーキテクチャ

設計判断

キューで受付と worker を分離し、SQL で受付済みと保存完了を区別します。Manual Ack は処理後に行い、Prefetch = 1 は設定したコンシューマー／チャネルの範囲で未確認配信を制限します。全体順序や厳密に一度の処理を保証する設定ではありません。復旧可能なファイルを保持し、ストリームを明示的に破棄します。

障害シナリオ

Blob 保存後、Ack 前に停止すると再配信されるため、既存オブジェクトと状態を照合します。WAITINGFILE の遷移・期限は再構築前に確認が必要です。NACK だけでは再試行戦略にならず、無限 requeue は問題メッセージを循環させます。DB 成功・発行失敗も照合対象です。outbox は将来の候補であり元実装の確認済み機能ではありません。

コンシューマーの Ack と発行側の確認は別の境界です。新規実装では発行確認、ルーティング結果、未発行の処理の照合も必要で、Ack だけではキューへの確実な発行を示せません。

信頼性の設計

少なくとも一度の配信を前提に、業務効果を冪等にします。ETag は版と条件操作に使うもので、汎用の内容ハッシュではありません。再構築時はサイズ・hash 検査を定義します。元の検証方式は独立確認していません。DLQ は拡張概念であり、再試行上限、安全な再実行、一時ファイル削除の復旧の検証が必要です。

セキュリティと権限

新規導入ではアップロードの認証とファイルごとの認可、認証情報の保護、パスとファイル名の検証、容量制限、保持・削除方針が必要です。これらは導入要件であり、元のシステムで確認済みの対策という主張ではありません。

トレードオフ

低 prefetch は未確認メッセージの負荷を抑えますが、システム全体が逐次処理になるわけではありません。一時保存はファイルにアクセスできるホストの復旧を助けますが、複製ストレージの代わりにはなりません。ホスト喪失、worker 間のアクセス、容量、孤立ファイルの削除を設計します。Hot／Cool はアクセス頻度、保持期間、取得費用で比較します。

期待する成果と受入確認

非同期の引き渡しと復旧の考え方を示す事例です。監査済みの遅延、稼働率、費用削減等は示していません。小規模検証では中断、重複、不完全な内容、ファイル不在、再試行上限を確認します。

技術と実装状況

  • ASP.NET
  • SQL Server
  • IIS
  • RabbitMQ
  • Azure Blob Storage
