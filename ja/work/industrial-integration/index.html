信頼性を考慮した産業機器連携の参考設計

デバイスイベント、オフライン状態、復旧可能な処理を中心に、リクエスト成功だけでは分からない障害を扱う計画です。

対象チーム

産業 IoT、ロボティクス、機器プラットフォームのエンジニア

成果と適用範囲

計画する受入条件：模擬機器のイベントを、再試行と重複排除を含む処理結果まで追跡できること。

根拠と対象範囲

合成データを使う参考設計の計画です。接続済み機器群や本番ロボットソフトウェアの実績ではありません。

この事例の内容

課題業務上の背景制約設計判断障害シナリオ信頼性の設計セキュリティと権限トレードオフ期待する成果と受入確認アーキテクチャ技術と実装状況

課題

通信切断、遅着、状態更新後の worker 再起動は部分的障害です。画面がこれらを端から端まで正常と誤認しない設計が必要です。

業務上の背景

テレメトリーを確認可能な業務イベントへ変える参考です。機器周辺の連携を対象とし、運動制御、安全認証、実機導入経験は主張しません。

制約

模擬機器のみで、一つの REST 経路と worker から始め、後に MQTT を検討します。ONLINE、OFFLINE、WARNING、ERROR、MAINTENANCE はメッセージ処理状態と別です。heartbeat の期限と古いイベントの扱いを定義します。

アーキテクチャ

設計判断

追記型のイベント履歴と最新状態を分離します。安定 ID で重複検出し、機器シーケンスやイベント時刻の規則で順序を扱います。永続化後に確認応答します。OFFLINE は一定時間に活動が見えないという観測で、物理故障の証明ではありません。

障害シナリオ

通信 timeout、重複、順序逆転、切断、遅延、再試行、worker 故障を注入する計画です。同一 ID で内容が異なれば競合です。古い正当なイベントは履歴に残しても最新状態を上書きしない場合があります。

信頼性の設計

再試行上限、終端状態、安全な再実行、相関 ID を定義し、固定時計で再現します。永続書き込み前後の中断でも二重の業務効果がないことを検証し、受付・キュー待ち・機器の生存状態を区別します。

セキュリティと権限

公開参考は合成 ID を使い、機器制御コマンドは含めません。実案件は機器認証、通信保護、入力制限、認可、認証情報の更新が必要です。模擬試験は本番・産業安全を証明しません。

トレードオフ

キューは疎結合に役立ちますが運用依存を増やします。少なくとも一度の配信には冪等性が必要です。厳密な順序は新しい更新を遅らせ、遅着許容には照合方針が必要です。

期待する成果と受入確認

将来は起動、障害注入、イベント・再試行の確認、最終状態の説明まで行えることを目指します。現時点でシミュレーターは未構築・未検証です。実案件は一つのイベント源とフローに限定して開始します。

技術と実装状況

  • 計画：.NET 取り込み API
  • REST を先行、MQTT は後続
  • キュー
  • SQL
  • TypeScript ダッシュボード

デモ・画面

稼働するシミュレーターや接続機器はまだありません。障害注入、状態 UI、画面は独立プロジェクトで整備予定です。

ソースコードの公開状況

industrial-integration-demo は独立 repository として計画中です。
